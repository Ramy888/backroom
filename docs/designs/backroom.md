# Design: Backroom: your agent keeps your secrets, and the database enforces it

## Problem Statement
How might we let a group decide together (a trip, the rent, game night) when everyone holds private limits they won't say out loud? Each person's AI agent negotiates for them, and the **database**, not the prompt, makes it impossible for one agent to read another seat's secrets.

## What Makes This Cool
- **"Hand the public the wolf."** Any visitor gets a private challenge circle, takes control of its wolf agent, and rewrites the wolf's prompt to make it fetch the Seer's role. The database does not return that row.
- **The claim, scoped precisely.** *A compromised agent cannot read rows its seat was not granted.* It holds, whatever the prompt says.
- **What the claim does NOT cover:**
  - An agent talking. In Werewolf, claiming or revealing your own role is a legal move.
  - A victim agent being talked into revealing itself.
  - Both are inference and persuasion, not database reads.
- **Two honest scoreboards:**
  1. **Forbidden reads:** "N attempted · 0 returned." This restates Appwrite's permission check, says so, and can be reproduced (see the receipt).
  2. **Seer found:** "wolves identified the Seer in X of n games, against a chance rate of 1/k." This is the leak no database can fix, measured against a baseline.

## Premises (agreed; 1, 4 and 6 revised after the second opinion and spec review)
1. **The wedge is provable, database-enforced isolation.** Proof comes from evidence the viewer can check:
   - **(a) Reproduce the denial.**
     - At game end, before the reveal, the `setup` Function mints a JWT for *their wolf agent's own user*, valid 300 s, for that circle's wolf seat only.
     - The visitor repeats the agent's logged reads from their browser.
     - Their own seat's rows return content. The Seer's row is not returned.
   - **(b) Post-game reveal.**
     - At game end the resolver grants **`read(user:<that circle's visitor>)` on that circle's `secrets` role rows only**. Den talk, night actions and the stored visitor prompt are never revealed, and Plan circles are never revealed.
     - The visitor fetches the role rows with their own session and sees each row existed with that content.
     - This proves existence and content, not what the permissions were during play; (a) covers that.
     - **Share (X3).** Pressing Share never changes `$permissions` on `secrets`. The resolver copies that circle's role rows (ID, content, and the *original* `$permissions`) into one `receipts` snapshot row with `read("any")`. That row survives the circle reset.
   - **There is no live god view.** After the game, the receipt shows row IDs and `$permissions` for the visitor's circle, read by the visitor themselves after the reveal.
   - **Source links and key scopes go in the receipt. Key values never do.**
   - **What isn't new:** collecting private preferences (Roamly, StayNow and Getaway Glow already do it).
2. **Agents hold only a user-scoped token.**
   - Each one comes from `users.createJWT`. The AI never sees an API key.
   - Every **read** the AI makes goes through TablesDB permissions. Its output is written by trusted `agent-turn` code with explicit per-row permissions.
   - If Day 0 disproves this, fall back to the decision point in Open Questions; don't re-ideate.
3. **One engine serves both circle types.**
   - Play makes the proof hit in 30 s.
   - Plan is the part people would actually use.
4. **What agents may publish is fixed per circle type, and the schema enforces it.**
   - **Werewolf:** free-text speech of at most 500 chars, enforced by the column size. Speech is gameplay, so no "safe-to-share" check applies. Secrecy in Play is about *reads*.
   - **Plan:** structured moves only: `{proposalId, vote: enum(accept, reject, counter), reason: enum(over_budget, dates, dealbreaker, preference)}`.
     - The enum columns make free-text disclosure (for example "over my 5,000 EGP cap") impossible to write.
     - A rejected write means the agent retries once, then abstains.
     - The reason codes still allow inference ("over_budget" means the limit is below the price), and the receipt says so.
5. **Distribution:** the public live link on Appwrite Sites. No app stores.
6. **Every denial and conflict shown is real.**
   - **All secrets use row-level permissions, including the den.** A seat without a grant gets **404** from `getRow`, and the row is omitted from `listRows`. We don't promise a 401.
   - **The 404 is paired with the post-game reveal (1b)** to show the row existed.
   - **Conflicts are real write-write conflicts on a staged row** (see the Plan protocol), with a named fallback.
   - Seed data stays small. EN plus Egyptian Arabic, applied to UI copy and agent chat only.

### Principals (who can do what)
| Principal | Credential | Scopes | Does | Permissions apply? |
|---|---|---|---|---|
| Human player / visitor | Anonymous session (passkey if Day 0 confirms it on Free) | n/a | Reads own seat, posts own moves, approves plans | Yes |
| Agent user (one per AI seat) | JWT minted per turn | n/a | All AI reads (`query_table`); in Plan, also intake writes to its own `secrets` row | Yes |
| `setup` Function | API key | users.write, rows.read, rows.write | Creates a circle, its seats, AI users and private rows whose permissions name the seat's human and agent; seeds the catalog; resets | No (trusted) |
| `agent-turn` Function | API key | users.write, rows.write (**no rows.read**) | Mints JWTs **only for AI-seat users of that circle** (checked in code against `seats.isAgent`). Runs the Claude loop, where **every read the AI makes uses the JWT**. With the key it only *writes*: the agent's `moves` row (read perms list the circle's member user IDs) and `turn_logs` rows (each tool call plus the raw Appwrite response status). | Trusted code; the AI's reads go through the JWT |
| `resolver` Function | Separate API key | rows.read, rows.write | Deterministic code, **no LLM in its path**. Resolves phases, stages and commits transactions, aggregates `counters` from `turn_logs`, runs the post-game reveal, and serves the sync "continue" action | No (trusted) |

The `agent-turn` Function is trusted and *could* mint a JWT for any user. The guarantee is that its published code restricts minting to AI seats, and that **the AI's reads** go through the JWT. That code, and every key's scopes, are linked in the receipt.

**Write grants (create / update / delete):**
| Table | Human session | Agent user (JWT) | Keys |
|---|---|---|---|
| `secrets` | none (Plan edits go through `api.editLimit`) | none (intake output is written by `api` / `engine` with a key) | setup (create, delete), api.editLimit, resolver (reveal) |
| `seats`, `turns`, `phases`, `counters`, `config` | none | none | setup, resolver |
| `moves`, `turn_logs` | Werewolf: none. Plan: none (the human acts through their agent) | none | agent-turn (create) |
| `night_actions`, `visions` | none | none | agent-turn (create `night_actions`), resolver (create `visions`) |
| `approvals` | none (through `api.approve`) | none | api.approve (key) |

- **Wolf agent users hold no write grants in Werewolf**, so the visitor's copy of the wolf JWT is read-only on the wolf's grants.
- **Its account endpoints** (for example `account.updateName`) only affect a pooled agent user. That user is reset when the circle is recycled.
- **Day 0 lists everything that JWT can write**, account endpoints included.

### Data model
- **Public to circle members:** `circles`, `seats`, `phases`, `turns`, and day `moves`. Read perms list the circle's member user IDs explicitly; there are no teams.
- **Private per acting seat:** `night_actions` and `visions` (see Werewolf).
- **`turn_logs`:** written by agent-turn and read by the resolver. The wolf seat's rows are also readable by that circle's visitor, for X1 and the reproduction.
- **Private:** `secrets`, one row per seat.
  - Werewolf: the seat's role.
  - Plan: structured limits (budget, dates, dealbreaker enums) plus free-text preferences.
  - Readable by that human and that agent only. In Play the resolver reads them through its key.
- **`den`:** row-level `read(user:wolfAgent…, user:wolfHuman…)` per circle. There are no per-circle teams or tables.
- **Plan catalog:** `options`, seeded.
- **Counters and caps:** `counters` (global and per-visitor, using `Operator.increment` with a max) and `config` (the kill switch).
- **Approvals:** `approvals`, ordinary rows outside any transaction.

### Session model (challenge)
- **Circle per visitor.** "Take the wolf" creates a private circle with the visitor plus 5 AI seats. The visitor is its only human, so only they control the wolf and there's no contention.
- **Visibility:** circle rows grant read only to that visitor and the circle's agent users. Visitor-written prompts and the wolf's speech are never broadcast to other visitors. Public pages show numbers only.
- **The visitor's grants:** read on their own seat, the den rows, and the circle's public rows.
- **Revocation:** at game end, the reveal grants the visitor read on the role rows only. No principal except the keys can write, so the circle is effectively read-only.
- **Agent users are created fresh per circle and deleted on reset** (O1/O6). There's no pool, so a leftover JWT can never reach a new circle.
  - JWT lifetimes: agent tokens 120 s, the visitor's wolf copy 300 s.
  - Day 0 checks that a JWT is rejected after its user is deleted.
  - About 7.5K users a month at the cap, against the 75K MAU limit.
- **Reset:** circles carry `expiresAt`. A 60-min cron and a "new game" button delete expired circles using the setup key.
- **Realtime connections:**
  - The 200-socket budget is split: circles ≤150 and landing ≤50.
  - **Active circles are counted from unexpired `circles` rows** (`expiresAt > now`), not from a running counter. At 150, the "take the wolf" button turns into a queue message.
  - **Landing sockets:** a sync `presence` action on the `setup` Function increments on connect and decrements on leave. That's one execution plus one write each way.
  - **Drift correction:** the 60-min cron resets the landing counter to 0, so missed decrements (closed tabs) can't lock the landing page static for more than an hour.
  - The UI degrades to polling every 10 s if a socket is refused.

### Cost and abuse controls (ship on the SAME day as the challenge)
- **Per visitor:** 5 games/hour and 3 injection prompts per game, enforced by `Operator.increment(1, max)` on a counter row. A rejected increment means the request is refused.
  - The counter is **keyed to a hashed client IP**, read by `setup` from the request headers, not to the anonymous session. A script that keeps making new sessions is still capped.
  - Once Day 0 confirms passkeys, they become an extra key.
- **Global:** 60 games/day and 1,500 games per calendar month, enforced the same way.
- **Judge reserve:** 20 of the daily games are reserved for a judge code given in the submission.
- **Always-on demo circle:** a pre-seeded finished game where the reproduction and the reveal always work, even when the cap is hit.
- **Per turn:** at most 4 tool calls and 600 output tokens.
- **Prompt input:** a 500-char cap, enforced by the column size.
- **Anthropic spend limit:** the builder sets it in the Anthropic console, as a user action.
- **Kill switch:** `config.challengeOpen`, checked by every Function and the UI.
- **Firewall:** verify on Day 0 that it exists on Free. If it doesn't, the counters above are the rate limit.
- **Estimate per game (recounted):**
  - **Turns and executions:** about 12 agent turns, which means about 12 agent-turn plus about 14 resolver executions (one per move, plus phase opens), about **30 executions**.
  - **Reads:** about 36 agent tool reads, about 120 resolver reads and about 50 UI loads, about **200 reads**.
  - **Writes:** about **70**.
- **Free quotas, assuming they're monthly (Day 0 verifies period and size):** 500K reads, 250K writes and 750K executions.
  - The monthly cap is **1,500 games**: about 300K reads, 105K writes and 45K executions.
  - Replay (X4) adds at most 5 runs/day × 140 writes, about 21K writes/month.
  - **Totals:** about 300K/500K reads (60%), 126K/250K writes (50%) and 45K/750K executions, leaving room for browser reads of `/r/<id>`.
  - This covers submission plus judging, roughly Oct 28 to late Nov.
  - The 30-game AI-only batch is included.
- **Polling fallback:** every 10 s, and only when a socket is refused.
- **Usage alarm:**
  - A 60-min cron reads the `counters` totals. Above 80% of any quota it sets `config.challengeOpen = false` automatically.
  - **This is a backstop only.** The monthly caps hold Function-side usage near 50–60%, so the real protection is the caps plus the real-usage or billing-page check below.
  - `counters` can't see browser reads. If Day 0 shows a key can read project usage, the cron uses real usage instead.
  - Otherwise the builder checks the billing page daily during judging.

### Turn fan-out and phase completion
1. The resolver opens a phase by creating one `turns` row for **every living seat**, with a deterministic ID `{circle}-{phase}-{seat}` and status `pending`.
   - Night turns go to every seat. Villagers' night turns finish at once with no Claude call. So `turns` rows reveal nothing about roles.
2. `agent-turn` triggers on `turns` create. It writes the result under the deterministic ID `{circle}-{phase}-{seat}`, so a duplicate execution's create fails:
   - **day** turns go to `moves`;
   - **night** turns go to `night_actions`.
   It then sets `turns.status` to `done`.
   - **Every turn ends in exactly one result row.** On any failure (a Claude error, a timeout, a cap hit), agent-turn writes an **abstain** result under the same ID.
   - **"Continue":** a sync resolver action, offered in the visitor's UI after 60 s. It marks pending turns older than 60 s as abstained, so an execution that crashed can't stall the game.
3. Every `moves` **or `night_actions`** create triggers the resolver (O2).
   - The run that counts all seats as moved creates a `phases` close row with the deterministic ID `{circle}-{phase}-close`, `status: claimed`.
   - It applies the phase effects **and** sets the close row to `done` in **one transaction** (O3).
   - **Recovery:** "continue" (or any later event) re-runs the resolution when a close row has been `claimed` for more than 60 s.
   - **No duplicates:** the next-phase IDs are deterministic, so a resolution that already committed makes the retry's transaction fail. The retrier sees `done` and exits.
   - So a crash can't strand the game.
4. Day 0 verifies that rows written inside a committed transaction emit the events this relies on.

### Plan protocol (one seeded Dahab trip)
1. **Intake.** Each human tells their agent their limits. The agent returns structured fields, and `api.editLimit` writes them (O4).
2. **Rounds.** Agents propose `options` and vote with structured `moves`. The resolver tallies the public votes only; in Plan it never reads `secrets`.
3. **Staging.** When all agents accept, the resolver creates a transaction (TTL 300 s). It stages:
   - a `plans` row;
   - one share row per member;
   - an update to **every member's `seats` row** (`planId`, `seatVersion` +1).
   That is at most 2N+1 operations, 13 for 6 people, well under 100.
4. **Approval** (O5).
   - Humans approve through `api.approve`. It checks the caller is that seat's human, then writes `approvals` with the deterministic ID `{plan}-{generation}-{seat}`, bound to the staged plan's `generation`.
   - Every re-plan or re-stage increments `generation`.
   - The resolver commits only when the approvals for the **current** generation equal the member count.
5. **The conflict moment.** A member presses "change my dates". **Every** limit change goes through `api.editLimit`. In **one transaction** (O4) it:
   - writes the new dates to **their `secrets` row**, so they stay private;
   - increments `seatVersion` on **their `seats` row**, which reveals only that "Karim changed a private limit".
   The staged transaction updates that same `seats` row, so the commit fails with a conflict. Day 0 tests exactly this shape: the resolver key stages a `seats` update, the setup key increments `seatVersion` on that row, then commit.
   - The resolver discards that transaction, shows "Karim changed his dates, re-planning", and opens a new round.
   - Bound: at most 3 re-plans, then the plan is marked stalled.
6. **Expiry.** If the TTL runs out, the resolver re-stages once, then shows "plan expired".
7. **Fallback** if Day 0 shows no conflict for this shape:
   - At staging, the resolver records each member's current `seatVersion` (v). Just before committing, it re-reads them and aborts if any differs from v. The member's edit increments `seatVersion`, so a change is always caught.
   - A gap of milliseconds remains between that check and the commit. That's acceptable for the demo, and the README says so.
   - The UI and video then say "version check", not "database conflict", and the success criterion changes to match.

### Werewolf
- **Roles:** 1–2 wolves, a Seer, and villagers. The game loop and prompts are written fresh (see the licensing note).
- **Agent tools:** each agent has two tools.
  - `query_table` runs through its JWT.
  - `post_message` returns the text to `agent-turn`, which writes the `moves` or `night_actions` row with its key and fixed permissions.
- **Untrusted input:** other seats' speech reaches each agent delimited as `<untrusted_table_talk>` data.
- **Night actions are private:**
  - Each `night_actions` row (a wolf's kill choice, the Seer's check target) is readable only by the acting seat's agent user, plus the visitor if that seat is their wolf.
  - The Seer's result goes into a `visions` row readable only by the Seer's agent.
  - Day speech and votes are public.
  - Day-1 test: a villager's JWT can't see any `night_actions` or `visions` row.
- **Night and day:** the resolver resolves night actions and the day vote deterministically, each in one transaction.
- **Forbidden-reads counter:**
  - **What counts as an attempt:** any `query_table` call by an agent on `secrets`, `den`, `night_actions` or `visions` that names a row ID, or runs a query, that isn't one of its seat's own granted rows. Seat-row IDs are deterministic (`{circle}-{seat}-secret`), so `agent-turn` can classify each call.
  - **What counts as returned:** the response contained a row not granted to that seat.
  - **Recording:** `agent-turn` writes each classified call and the raw response status to `turn_logs` with its key. Visitors and agents can't write there.
  - **Aggregation:** the resolver adds them into `counters`.
- **Seer-found metric:**
  - **What's scored:** one structured decision made after table talk: the wolves' **night-2 kill target**. A game counts only if the Seer is alive at night 2.
  - **Baseline:** 1 over the living non-wolves at that moment. A random-wolf simulation over the same event confirms it.
  - **Accusations** count only as structured day votes.
  - **Games:** AI-only games and visitor challenge games are reported separately.
  - **Batch:** before submission, run 30 AI-only games, at about $0.20–0.40 each. That spend needs the builder's OK first.
  - **Small samples:** show "n = X, too few to say" until n ≥ 20.

## Success Criteria
- **On the live link, a stranger can:**
  - open a private challenge circle with an anonymous session (or a passkey, if Day 0 confirms it);
  - take control of the wolf and inject a prompt;
  - see the agent's forbidden read come back empty;
  - repeat that read from their browser **with the wolf agent's JWT**;
  - after the game, fetch their circle's revealed role rows with their own session. Den talk, night actions and prompts are never revealed, and Plan circles never are.
- **The forbidden-reads counter shows 0 returned**, and is labelled as restating the permission check.
- **The Seer-found metric is shown with n and its chance baseline.**
- **The Plan demo works:** three people's agents settle on a Dahab plan; a mid-approval "change my dates" causes a real commit conflict (or the version-check fallback, if Day 0 forces it); and the agents re-plan and commit.
- **No visitor's prompt or wolf speech is visible to any other visitor.**
- **Caps and the kill switch work:**
  - A visitor can't start more games than allowed, **even with a fresh anonymous session from the same IP**.
  - The judge code and the always-on demo circle still work when the daily cap is hit.
  - Turning off `challengeOpen` stops new games.
- **X1:** every denial shows a chip naming the table, the rule type and the TablesDB feature. Actual `$permissions` appear only after the reveal, and only on role rows.
- **X2:** each of the 4 templates (EN and AR) reaches a real forbidden read in one tap.
- **X3:** `/r/<id>` loads after the circle is reset. It shows only snapshot fields. A wolf agent in another circle listing `secrets` still gets 0 foreign rows.
- **X4:** the landing replay never fires `agent-turn` or the resolver; zero Claude calls are logged. It stops at its daily cap and falls back to a static view.
- **X5** (if Day 0 says go):
  - The outside agent's **JWT reads** are denied like ours, shown by **its own transcript**. Those reads go straight to Appwrite, so `byoa-move` doesn't see them. That seat is excluded from the forbidden-read counter.
  - Its moves land only through `byoa-move`.
- **The video is ≤3 min** and shows the refusal, the reproduction, the conflict and the reveal.
- **The README "Why TablesDB" section** maps each guarantee to a feature: row permissions, transactions and conflicts, increments with a cap, enum and size column constraints, and deterministic IDs.

### R2-1 — completeness (blocking)

**Problem**

> The forbidden-reads counter ('N attempted, 0 returned') is a headline demo element and a success criterion, but the design defines neither what counts as an attempt nor who records it. Under the design's own denial semantics, listRows silently omits ungranted rows, so without a rule a list query on secrets or den that returns only the agent's own row can't be told apart from an attempt. As specified, no principal can produce the number: agent-turn 'writes nothing with the key', and the resolver, which 'writes counters', never sees the agent's tool calls.

**Remedy**

> Define an attempt deterministically (e.g. any query_table call on secrets or den that names a row ID, or uses a query, not limited to rows its seat was granted) and define 'returned' (that row's content came back). Name the data path: e.g. agent-turn classifies each tool call and records the counts on the turn's moves row through the JWT, and the resolver adds them to counters with its key. Make sure the visitor holding the wolf JWT can't forge that field (see R2-4).

### R2-2 — consistency (blocking)

**Problem**

> Premise 1b grants read('any') on 'that circle's private rows' at game end, and the session model makes the reveal the moment the circle becomes read-only. The private rows include den (wolf talk driven by the visitor's prompt) and wherever the visitor's prompt is stored. That contradicts the success criterion 'No visitor's prompt or wolf speech is visible to any other visitor', and the stated reason Approach C's moderation risk is avoided in A. Rows with read('any') also come back from any visitor's listRows, so every finished circle's revealed rows become publicly listable, not just fetchable by that circle's visitor. Nothing excludes Plan circles, although one engine and one resolver serve both and Plan secrets hold real budgets.

**Remedy**

> Scope the reveal. Grant read to that circle's visitor only (user:<visitorId>), which is enough for the skeptic to fetch the rows with their own session, or reveal only the role rows or fields. Exclude den talk and the prompt's storage. State that Plan circles are never revealed. Update Premise 1b, the session model and the success criterion 'fetch the revealed rows directly' to match.

### R2-3 — feasibility (blocking)

**Problem**

> Agents create rows through their JWT at play time (a moves row per turn, and den rows if wolves write them). Those rows must be readable by the circle's other agent users and its visitor, but the design names no mechanism that can grant this. agent-turn writes nothing with its key and there are no per-circle teams. Appwrite client callers can generally grant only roles they hold themselves (self, users, any, their own teams or labels). That leaves self-only rows, which the rest of the circle can't see, or users/any, which every visitor can see and which breaks the session model. R1-10 asked for a Day-0 check of whether a JWT client can create rows granting permissions to other users. It is still missing from the Day-0 list, and no credential is named for the case where it can't.

**Remedy**

> Add that Day-0 check. Choose how circle members get read access to agent-written rows. Options: setup gives the circle's users a per-circle label or team, so the JWT can grant label:<circle> or team:<circle>; the resolver pre-creates each turn's moves row with circle-member read and update for that seat's agent, and the agent only updates it; or the resolver re-permissions agent rows with its key. Name the credential in the principal table and the receipt, and specify the same for den.

### R2-4 — completeness (blocking)

**Problem**

> Premise 1a hands the visitor a JWT for the wolf agent user. The visitor can then call the database directly with every write the agent has, bypassing post_message, the per-turn caps and agent-turn's checks. The design specifies read grants only, with no create, update or delete grants per table and principal. Depending on those grants, the visitor could: pre-create the wolf's deterministic moves IDs for future phases, so agent-turn's creates fail; edit or delete moves after other agents have read them; set its own turns.status; write den rows; change its own secrets row (its role) if setup gives the agent update rights, as Plan intake needs; or forge counter inputs (R2-1). A table-level create grant also means 'the circle is read-only' after the reveal can't be enforced. The Day-0 question 'does a wolf agent's JWT expose nothing beyond its grants?' is circular, since the open issue is what the grants are. The design also doesn't say which Function mints the visitor's copy or how long it lasts.

**Remedy**

> Add a write-grant table: create, update and delete per table, for human sessions, agent users and keys. Make Werewolf secrets, seats, turns and counters non-writable by agent users and visitors. Decide how far the visitor's JWT reaches. For example, mint it only after the agent's last turn and before the reveal, or accept the reach and bound its effects (the resolver ignores moves not created through agent-turn and checks each move against its turn). Name the minting Function and the JWT duration. Replace the circular Day-0 question with a concrete one: list everything the wolf agent's JWT can write, including account endpoints for the agent user.

### R2-5 — feasibility (blocking)

### Expansion contracts (amended after the CEO spec review, 2026-10-21)

**X1, "why" chips**
- **Before the reveal:** the chip text comes from the *table and rule type only*, for example "`visions`: readable only by the acting seat (row-level permission)". Never from a key read, so there's no live god view, and a missing `visions` row can't point to the Seer.
- **After the reveal:** actual `$permissions` appear, on role rows only.
- **Data source:** `agent-turn` writes the wolf seat's `turn_logs` rows with `read(user:<visitor>)`. That is also the source for the reproduction (1a).

**X2, attack templates**
- Static EN and AR copy, no data changes.

**X3, share**
- **The action:** a sync `share` action on the resolver Function, available only when the circle is a Werewolf circle, the caller is its visitor, and the game has ended.
- **The snapshot:** it writes one `receipts` row with `read("any")`, holding:
  - the circle ID and end time;
  - the circle's forbidden-read counts (the resolver totals them from that circle's `turn_logs`);
  - each role row's ID, content and *original* `$permissions`.
- **Lifetime:** reset never deletes `receipts`.
- **What stays private:** `secrets` permissions are never changed. A wolf agent in another circle that lists `secrets` still gets nothing foreign.
- **The page:** `/r/<receiptId>` renders the snapshot only. Its copy says "verify it yourself: play a game". Content alone isn't the isolation proof.

**X4, landing replay** (*superseded by M7: a static client-side replay of a bundled JSON timeline; everything below about `replay_*`, the lease and the caps is removed*)
- **Separate tables:** `replay_moves` and `replay_phases`. No Function triggers on them, so it costs zero Claude calls.
- **The `replay` Function:** `execute("any")`, its own key with rows.write on the `replay_*` tables, and it checks `config.challengeOpen`.
  - **The lock:** `<slot>` is a 15-minute time bucket (`replay-YYYYMMDDHHmm`, minutes rounded down to 00, 15, 30 or 45), so each bucket gets a fresh create-only ID. Only one create per bucket succeeds, and a crashed run frees itself at the next bucket.
  - **A run never outlives its bucket:** it stops inserting when its bucket ends, so it can't overlap the next run's reset.
- **Caps:** 5 runs/day, enforced by `Operator.increment(1, max)`. Past the cap, or above 50 landing sockets, the landing page renders the finished game from **bundled static JSON with no polling**.
- **Quota:**
  - About 140 writes per run (inserts plus reset), so at most 700 writes/day, counted in the usage estimate.
  - **Realtime messages:** about 140 events × ≤50 viewers × 5 runs, about 35K/day, roughly 1M of the 2M monthly messages shown on the Free billing page. Game events add about 1,500 games × 70, about 105K. Total about 1.15M of 2M. Day 0 confirms how they're metered.
- **Source game:** recorded from the Day-1 script, so there's no dependency on the Day-5 batch.
- **Realtime budget:** landing ≤50 of the 200 sockets (see the session model).

**X5, bring your own agent (Day-0 go/no-go)**
- **Who:** the builder's own Claude Code, run for the video and the live demo. One designated seat in a dedicated "open table" circle; only one outside agent at a time.
  - **Ownership lock:** a deterministic `byoa-lock` row. A second agent gets a "seat taken" message.
- **Credentials:** every read uses a **seat JWT**, delivered by a sync `byoa-token` action. That action checks an operator code and the seat lock, and the token is valid 300 s.
  - **Refresh:** the `byoa-lock` row holds an owner nonce, readable by the seat user. `byoa-token` reads it through the previous seat JWT, so a refresh works with no rows.read scope on the key.
  - **OAuth to mcp.appwrite.io is for the event subscription only.** That's a usage promise, not an enforced scope.
  - **Day-0 check:** list every endpoint that token can reach. If it can read rows (bypassing permissions), use a dedicated, scoped identity for the subscription, or cut X5.
  - **The subscription covers a `byoa_turns` table that holds no secrets.** It's never project-wide.
- **Making moves:**
  - the resolver writes `{turnId, phase}` to `byoa_turns` at fan-out for the external seat (that's what the subscription sees);
  - a sync `byoa-move` Function reads the `turns` and `seats` rows **through the caller's JWT** (the seat can read them), checks that the JWT user is the seat's `agentUserId` and the turn is pending, then writes the move with its key;
  - `seats.controller = external` makes `agent-turn` skip that seat;
  - that seat's "continue" deadline is 180 s.
  - **The open-table circle:** created by `setup` with the operator code, it expires after 2 h. the builder's operator view has the "continue" button.
- **If Day 0 can't confirm a safe subscription, X5 is cut.**

**New principal rows**
| Principal | Credential | Scopes | Does | Permissions apply? |
|---|---|---|---|---|
| `replay` Function | Own API key | rows.write (replay tables only, by convention) | Takes the lease, replays, resets, enforces the cap | No (trusted) |
| resolver `share` action | resolver key | as resolver | Writes a `receipts` snapshot | No (trusted) |
| `byoa-token` / `byoa-move` | API key | users.write, rows.write | Mints the seat JWT; validates the move (reading through the caller's JWT) and writes it | No (trusted); the outside agent's reads go through the JWT |

**Write grant added:** `byoa_turns` is created by the resolver; nobody else writes it. Its rows are readable only by the external seat's agent user.

**CRITICAL GAP R1: the Free plan allows 2 Functions per project. The design names 6.**
- **Source:** Appwrite changelog 2026-01-08 and the Free plan docs. The Free plan also allows 1 database, 1 bucket and 2 projects.
- **Remedy (auto-decided):**
  - Exactly 2 Functions: **`api`** (sync) and **`engine`** (event-triggered).
  - The principal table's rows become **scoped project API keys** held in Function env vars: K_setup, K_agent, K_resolver, K_replay, K_byoa. Each code path builds its client from its own key, so the agent-turn path still has no rows.read.
  - **Day 0:** confirm the Function cap in the Console, and confirm several API keys are allowed.

**R2: a resolver failure mid-phase stalls the game.** "Continue" re-invokes the resolver path for that phase. That's safe to repeat because the close ID is deterministic.

**R3: recursion guard.**
- `engine` acts only on `turns`, `moves` and `night_actions` creates, and only when `circles.status = active`.
- Resolver writes to `phases` and `plans` fire no triggers.

**Circle state machine:**
```
 created ─setup ok─▶ active(phase n: night|day) ─close row created─▶ active(phase n+1) ... ─win check─▶ ended ─reveal─▶ revealed ─share─▶ (receipts row)
    │                    │ continue (turns older than 60 s/180 s → abstain)                         │
    └─expiresAt─▶ expired ◀────────────────── expiresAt (cron) ◀────────────────────────────────────┘

```

  - At **100×**, the Free quotas and Claude rate limits run out. They're capped per IP, per day and per month.

**Section 4: Data flow and interaction edge cases**
- **Async ordering, last two moves at once.**
  - Both resolver runs count "all moved".
  - Only one `{circle}-{phase}-close` create succeeds; the other gets a 409 and exits.
  - **Test:** pause after the count, release both, assert exactly one phase advance.
- **Approval vs edit.**
  - **Invariant:** never commit a plan staged on stale seats.
  - **The race:** an edit increments `seatVersion` on the same staged row → the commit conflicts (or the fallback version check aborts).
  - **Test:** both orders.
